# CLAUDE.md — VITAL project guide for coding agents

This file orients a coding agent (or a future you) working in this repo. It
is deliberately blunt about what's solid, what's fragile, and what's
genuinely unresolved — this project was put through an honesty audit and
several rounds of real-data validation; don't undo that by re-introducing
claims the code doesn't back up.

**For the full chronological story** (every bug found, every fix tried
including the failed ones, every real number, in the order it happened),
see [`data/EVOLUTION.md`](data/EVOLUTION.md). This file is the short/brief
version — that one is the detailed one.

## What this project is

VITAL (aka "Opti-Screen") is a college project: contactless vitals
extraction via webcam rPPG, feeding a CrewAI 3-agent "triage" pipeline that
classifies ESI acuity and Compensated Shock, displayed on a Next.js
dashboard with a Flask API backend and Neon serverless Postgres. See
[README.md](README.md) for the full architecture, feature list, and
Validation section — read that before this file for context; this file is
about how to work in the code, not what it does for a user.

## The one rule that matters most here

**The deterministic clinical engine (`core/clinical.py`) is the sole source
of truth for ESI level, Compensated Shock flag, and priority score. The LLM
agents (`agents/`) narrate and explain that output — they never compute or
override it.** This was NOT always true; an earlier version let the
Coordinator Agent freely generate these numbers as JSON, parsed with regex,
falling back to a hardcoded `esi_level=3` on any parse failure. If you're
touching `web/routes.py::triage_run_api`, `agents/crew.py`, or
`agents/config/tasks.yaml`, preserve this separation. Don't let an LLM
compute a number that drives real triage priority.

## Known-good vs. known-fragile (read before touching)

**Solid, tested, trust these:**
- `core/clinical.py` — unit-tested against 8 hand-built clinical scenarios (normal, isolated tachycardia/tachypnea, borderline/severe shock, bradycardia, low-SQI, no-signal). Any Compensated Shock flag forces `needs_manual_review=True` unconditionally — don't remove that, it's a deliberate safety policy, not a confidence heuristic.
- CHROM on synthetic signal: 0.29 BPM MAE / 0.53 RMSE across 50-140 bpm under 2% sensor noise (`python scripts/validate_dataset.py`).
- The concurrency fix in `agents/crew.py` (`build_triage_crew()` factory, not a module-level singleton) — CrewAI `Task` objects store output on `self` and are not safe to re-enter from concurrent Flask threads.
- `web/neon_db.py::get_all_patients()` now raises on a real DB failure instead of returning `[]` — do not revert this. It used to make a transient Neon cold-start connection hiccup indistinguishable from "the queue is genuinely empty," which looked exactly like data loss to an end user. Every caller must catch and surface the error, not swallow it.

**Fragile / partially fixed, do not overclaim:**
- **CHROM on real video (classical DSP only, no ML correction): 9.4 BPM MAE / 16.5 RMSE across 71 real sessions (41 UBFC-rPPG + 30 UBFC-Phys)**. This is *after* three independent DSP-layer fixes below (was 17.4/24.1 MAE/RMSE before any).
- **Hybrid classical-DSP + ML correction layer (`scripts/build_ml_dataset.py`, `scripts/train_correction_model.py`, `scripts/validate_with_correction.py`, `models/`): 6.48 BPM MAE / 9.66 RMSE across the same 71 sessions**, every one evaluated out-of-fold (never on a subject the correction model trained on). Uses Huber loss (`gbr_huber` in `_build_models()`), not squared-error — measured small-but-real win, 8.80→8.67 MAE per-cycle, 6.65→6.48 MAE at the session level (`data/evolution/12-huber-loss.md`). Biggest single win: the speech-condition motion-artifact gap, untouched by every DSP fix below, dropped from ~21-23 to ~8-9 MAE. Bigger models (deeper GBR, bigger regularized MLP, an ensemble) were tested and did NOT beat the small deployed model — real constraint is 56 unique people, not 242K training rows; see `data/evolution/10-bigger-models-dont-help.md` and `data/evolution/11-more-subjects.md`.
- **Bug #1 — harmonic lock-on: two fix attempts failed, a third worked (partially).** Root cause: the peak-picker was locking onto ~0.5×/2× the true rate for sustained stretches, reproduced across all three datasets (first found on `test/dataset_2/subject41`).
  1. Debounced BPM lock/candidate hysteresis (`AdvancedRPPG._resolve_bpm_lock`) — verified via trace to work exactly as designed, **zero aggregate improvement**: the false lock wasn't noise-driven flip-flopping, so debouncing didn't help.
  2. Naive upward-summing Harmonic Product Spectrum (first version of `_select_dominant_freq_hps`) — **zero change**, and provably wrong-direction: for a signal stuck at half-rate, the true signal's own energy sits exactly at that candidate's "2nd harmonic" position, so naive HPS scores it as support *for* the wrong answer.
  3. **What worked**: asymmetric subharmonic-promotion (current `_select_dominant_freq_hps` — misleading name, kept for history; see its docstring) — explicitly checks whether the top candidate's *double* has comparable-or-greater power, and promotes to it if so. Real, measured wins: `subject41` 52.6→8.2, `subject46` 41.2→1.3, `subject49` 36.5→0.4, `subject9` 60.9→2.8, `subject34` 63.0→0.5 BPM error.
  - **Honest downside, do not hide this**: introduced new regressions — `dataset_1/after-exercise` (11.0→32.9 final), `subject22` (41.0→46.8), `subject24` (5.9→20.4), `subject32` (6.0→19.3), `subject37` (4.8→21.0, **since fixed, see below**), UBFC-Phys `s4` speech (9.6→22.5). `after-exercise`/`subject22`/`subject24`/`subject32`/`s4`-speech are still unresolved, not yet root-caused the way subject41/subject25 were — a real, open item.
  - **A third, unrelated bug — found by tracing `subject37`'s regression**: `get_final_summary()`'s history-append gate (in `process_ppg_signal()`) rejects any reading more than 18bpm from the median of the last 5 *accepted* readings — meant to filter single-frame noise, but if the first few accepted readings land during a brief wrong cold-start burst, every later correct reading gets rejected forever (the anchor never updates). `subject37`'s whole-session history ended up with 7 entries, all from an 82-89bpm burst in the first couple of seconds, while the correct ~58bpm signal that dominated the rest of a 2000-frame clip was discarded throughout. **The first fix attempt (unconditionally allow re-anchoring after a long enough sustained-disagreement streak) fixed subject37 but broke subject41** — dropping it from 8.2 back to 41.8 BPM error. Tracing why showed subject41's per-cycle readings are *still* genuinely bimodal across the whole clip even after subharmonic-promotion (~983 vs ~933 reading split in one trace) — meaning the original "subject41 fixed, 8.2 error" result was never a real resolution; it was this exact freeze bug accidentally anchoring on the correct cluster early and never letting go. **Fixed correctly** by only allowing the escape hatch while the frozen anchor is still small (`_HISTORY_UNSTICK_MAX_HISTORY = 10` in `core/rppg.py`) — genuinely-untested cold-start-fluke territory — never once it has accumulated substantial support. Verified: subject37 stays fixed (21.0→**6.0**), subject41 fully restored (**8.2**, unchanged), other regressions untouched either way (confirms they have a different cause). Full story: `data/evolution/09-history-freeze-bug.md`. **Lesson worth repeating from Era 4: a fix that "looks right" and even improves the one case it targets is not verified until you re-run the OTHER known-good cases too — subject41 was the project's flagship success and the naive version silently destroyed it.**
  - **Validation gotcha that cost real debugging time**: `scripts/validate_dataset.py`'s manifest path used to pass `process_stride=2` to `analyze_video_complete()`. The BPM lock/subharmonic logic counts in *cycles* (calls to `process_ppg_signal()`), not real time — striding silently doubled its effective time window and changed tracking *behavior*, not just speed. A direct stride=1 trace showed a real fix; the same video through the strided batch script showed no change. Fixed by keeping `process_stride=1` (default) on this path — UBFC-rPPG/Phys clips are short enough not to need it; stride stays reserved for rPPG-10's genuinely long (10 min) clips in `validate_cropped_roi.py`, which has no cycle-counted hysteresis in play.
  - **Second gotcha, same debugging session**: `scripts/analyze_video.py::analyze_video_complete()` used to compute its final BPM as a plain mean of the *last 10 readings* — a completely different algorithm than `AdvancedRPPG.get_final_summary()`'s IQR-filtered full-history median, which the live webcam path already used. Fixed: `analyze_video_complete()` now sources `final_bpm` from `get_final_summary()` too.
- **Bug #2 — hardcoded fps=30, found by tracing `subject25` (a completely different failure signature from subject41: rock-stable and confident, wrong the whole clip, not oscillating).** Its video is actually 23.2fps; every `AdvancedRPPG` construction site hardcoded `fps=30` regardless of the source's real frame rate, which deterministically scales every frequency by (assumed/actual) — 91.5 true bpm × (30/23.2) ≈ 118, matching the observed error almost exactly. Fixed via `Camera.get_source_fps()` (`core/camera.py`) used at every construction site (`scripts/analyze_video.py`, `web/routes.py::_reset`). Verified: `subject25` 23.5→3.5, `subject26` 25.5→2.5 BPM error. **If you add a new `AdvancedRPPG(...)` construction site anywhere, use `camera.get_source_fps()`, do not hardcode 30 again.**
- **Stratified-by-condition accuracy** (UBFC-Phys labels rest/speech/arithmetic) — after both fixes: arithmetic 3.5 MAE, rest 6.5 MAE, **speech 23.4 MAE, essentially untouched by either fix** (was 26.1/26.6 before). This is real signal, not noise: speech/talking is a *different* problem (motion artifact from mouth movement) than either bug just fixed (frequency-domain ambiguity, fps mismatch) — don't expect future DSP fixes in this family to touch the speech number.
- POS algorithm (`algorithm="POS"` in `AdvancedRPPG`) — present in `core/rppg.py`, **not wired into any API route or UI control** — every instantiation site hardcodes CHROM. Don't "fix" this by wiring POS into the app without full re-validation first. Its harmonic lock-on was root-caused (Era 14): it overshoots to ~2x the true rate from the very first cold-start reading — the mirror image of CHROM's undershoot bug — and a symmetric "demote if the half has comparable power" check in `_select_dominant_freq_hps` fixed that specific pattern (synthetic MAE 26.71→16.00, zero effect on CHROM's numbers). Two of seven synthetic cases and real-video testing (first ever run against real subjects) still show unresolved harmonic errors in both directions — this is a genuine partial fix, not a resolution. See `data/evolution/14-pos-subharmonic-demotion.md`.
- **Respiratory rate — rewritten in Era 19 after finally getting real ground truth, and the old implementation turned out to be measuring nothing at all.** Full story: `data/evolution/19-respiratory-rate-ground-truth.md`.
  - **Ground truth now exists**: BIDMC PPG and Respiration Dataset (PhysioNet, in `dataset/`) — 53 x 8-min recordings with breath annotations from TWO independent human annotators. Harness: `scripts/validate_rr_bidmc.py`. **This is contact pulse oximetry, not webcam video** — it validates the RR extraction DSP on a clean signal, NOT the camera/ROI layer, and does NOT prove the same accuracy on a noisier webcam waveform. Same distinction as `validate_cropped_roi.py`.
  - **The old estimator scored r ≈ 0 against human-annotated breaths** (+0.048 over 53 recordings). 97% of its readings sat on a band edge (~72% at the 6 br/min floor, ~25% at the 30 br/min ceiling) while truth was 15-24. Its docstring claimed the multi-segment Welch rewrite had fixed the "bounces between 6 and 30" symptom; it had not. The `rr_conf < 30` gate suppressed **99.7%** of readings, which is the only reason users saw missing RR rather than wrong RR — that gate was doing real safety work.
  - **Root cause was `_safe_butter_sos` silently building a HEART-RATE filter.** Its pulse-band guards (`_BP_LOW_FLOOR = 0.70`) rewrote the requested 0.10-0.50 Hz respiration band into **0.70-1.00 Hz = 42-60 breaths/min**, centred on the heart-rate fundamental — verified with `sosfreqz`. The "respiration filter" was *passing the pulse, not rejecting it*. **If you call `_safe_butter_sos` for any band outside the pulse range, you MUST pass `clamp_to_pulse_band=False`** or you will silently get a 0.70-1.00 Hz filter again. The default stays True so every HR call site is bit-identical.
  - **Buffer length was a red herring** — a tempting information-theoretic argument (10 s buffer = 0.1 Hz resolution ≈ 6 br/min cells; 2 breath cycles at 12 br/min) but sweeping 10 s -> 60 s moved MAE only 12.74 -> 11.21. Resolution can't help when the signal isn't in the band. RR does now use a 60 s window, but that mattered only *after* the filter was fixed.
  - **Current implementation: RIV fusion, 2-channel** (Pimentel/BIDMC + Karlen SmartFusion) — respiration is derived from two per-heartbeat features, RIAV (amplitude) and RIIV (baseline), resampled onto a uniform 4 Hz grid via **cubic spline** (not linear — see below), detrended, filtered, and fused by **median**. Resampling to 4 Hz is what structurally kills pulse leakage — Nyquist 2 Hz decimates the pulse away by construction. A third RIV (RIFV, beat-interval/RSA) is extracted but **deliberately excluded from fusion** — measured alone on BIDMC it scored slope 0.09-0.14 / corr ~0.08 (near-noise, likely because this ICU population's RSA is blunted by ventilation), and including it in the median dragged the fused answer toward its bad guesses.
  - **Measured (all 53 recordings, deployment-faithful 30 fps, FINAL after Finding 8's harmonic-demotion fix): per-window MAE 2.39, session-level MAE 1.59, median error 0.40, correlation +0.395, 83.0% of sessions within 2 br/min.** Legacy (pre-Era-19) on the same harness: session MAE 4.56 from the single recording that produced a number at all — current is a ~3x improvement over the original.
  - **Two more real bugs found and fixed after the first RIV-fusion pass shipped, both caught by the synthetic RR self-test regressing** (see the "trust changes" note at the top of this file — this is that lesson happening again):
    1. **`rr_history` was silently duplicating every reading ~15x.** RR is only *recomputed* once every `_RR_UPDATE_HZ` (2 Hz), but the append to `rr_history` used to run on every single frame regardless — so one true estimate got appended once per frame until the next recompute (~15 copies at 30 fps). This meant a reading's influence on the session median was proportional to how many frames elapsed before the next recompute, not to how likely it was correct. A single wrong-but-confident cold-start estimate could dominate the IQR-filtered median purely by being duplicated more. Fixed by gating the append on the same `is_fresh_rr` flag that gates the recompute — one append per true estimate. This alone measurably improved the real BIDMC number (session MAE 2.14 -> 1.60), so it wasn't just a synthetic-only fix.
    2. **Beat detection for RIV extraction (`_extract_rivs`) over-counted beats by ~55%.** Its pulse filter (`_sos_pulse`) was a *static wide band* (`_BP_LOW_FLOOR`.._BP_HIGH_CEIL` = 42-180 bpm) that passes a heart rate's 2nd harmonic completely unattenuated whenever the harmonic also falls in-range — which it almost always does (2x 60 bpm = 120 bpm, itself a plausible heart rate). Any dicrotic-notch-shaped waveform then has a second local maximum per cardiac cycle that a generic prominence threshold cannot always reject. Verified directly: a synthetic signal with a KNOWN, confirmed 60 bpm heart rate and **no respiration at all** produced 91 detected "beats" over 58.6 s (1.55 Hz) instead of the true 58.6 (1.00 Hz) — proving this was never a respiration-specific bug. Fixed with `_beat_detection_filter()`, which narrows the pulse-band filter to the CONFIRMED heart rate (`self.prev_bpm`) ± 25% once one exists, mirroring how the main HR pipeline's adaptive filter already solves the identical problem for its own peak-picking. Verified fix: same synthetic case now detects 58 beats at 1.02 Hz. This did not change the aggregate BIDMC number (real PPG morphology apparently doesn't trigger the bug as severely as the synthetic generator's explicit 2nd-harmonic term) but is a real, verified robustness fix against a documented failure mode, and it resolved a specific synthetic-case regression (RR=12 br/min case had jumped to a confidently-wrong 27.1 br/min — almost exactly 2x — before this fix).
  - **STILL UNRESOLVED, do not overclaim: systematic shrinkage toward the population mode, i.e. estimates compress toward ~17-18 br/min instead of tracking the true rate.** Reframed from "high-RR underestimate" to what it actually is: regression of estimate-on-truth has slope 0.339 (1.0 = unbiased) — the estimator moves only a third as much as reality. Cubic interpolation (vs. the original linear interpolation between beat-spaced ~0.7s samples, which acts as a mild low-pass and was measured to contribute real bias) improved the slope to 0.541 — a real, verified win — but the dominant cause of the remaining shrinkage is still unknown. Tested and refuted: gate/selection bias (ungated slope 0.339 vs gated 0.307 — gate isn't the cause), widening `_RESP_HIGH` (swept 0.50/0.60/0.70/0.95 Hz: bias barely moved), multi-segment Welch sub-windowing (measured WORSE than the current full-span periodogram, not better — more variance from shorter windows). **This still biases toward MISSING tachypnea** — the dangerous direction, since `RR_TACHY` is 20 and suppressed tachypnea also suppresses the Compensated Shock term. Treat any specific "N% miss rate" figure as a flagged risk, not a stable measured rate — the underlying n of true-tachypnea BIDMC recordings is small (5).
  - Also unresolved: `bidmc_32`/`bidmc_33`/`bidmc_36`/`bidmc_43` remain large per-record outliers (session error 6-16 br/min) even after all fixes above; synthetic RR MAE (~6.7-6.9) is still much worse than real (1.60) — either the generator is unrealistically hard or it probes a weakness BIDMC's mostly-15-24 br/min distribution doesn't.
  - **Second independent dataset confirms it: CapnoBase (`scripts/validate_rr_capnobase.py`, 42 anaesthesia/surgical recordings, capnography ground truth, different institution/population from BIDMC).** Format gotcha: ships as MATLAB v7.3 (HDF5) — needs `h5py`, not `scipy.io.loadmat`. Data gotcha: record `0133`'s own shipped ground truth contains 5 literal `inf` values — filter non-finite ground truth before aggregating, or one bad sample poisons the whole MAE to `inf`.
  - **Traced CapnoBase's worst outliers to two distinct mechanisms and fixed one (Finding 8).** (1) `0115`/`0018`: true RR ~35-40 br/min, physiologically outside the `_RESP_HIGH` 30 br/min ceiling — not a bug, a structural search-band limit (widening the band was already shown not to help, for a different reason — see the shrinkage bullet above). (2) `0105` (steady true RR ~10, gold well inside the band): a genuine **2x harmonic lock**, confidently wrong — alternated between correct and exactly-double for minutes at a time, with confidence HIGH (82-100%) on the wrong windows and LOW (1-3%) on the rare correct ones, because two RIV channels agreeing on the same wrong harmonic looks like strong agreement. Verified physiologically real (not filter leakage) by inspecting the raw spectrum directly — real 2nd-harmonic energy exceeded the fundamental in the affected windows. **Fixed with `_demote_harmonic`**, the mirror of the existing `_promote_subharmonic` (checks the peak's HALF instead of its double) — `_promote_subharmonic`'s own docstring had already predicted this mirror would eventually be needed.
  - **A shared threshold with promotion (0.55) improved CapnoBase but regressed BIDMC (1.60 -> 1.87) — a real trade-off, not a free win.** Swept a *separate* `_RR_DEMOTE_RATIO` on 20+20-record subsets and found a genuine non-trade-off optimum at 0.75-0.85 (BIDMC's subset MAE there was *better* than with demotion disabled entirely, while CapnoBase kept nearly all its gain). **Set to 0.80, confirmed on full datasets: both improved simultaneously — BIDMC session MAE 1.60 -> 1.59, CapnoBase 3.37 -> 2.51, median 0.20 -> 0.07.** CapnoBase now **beats** published SmartFusion on within-2-br/min rate (83.3% vs 78.6%) and median (0.07 vs 0.35), though session MAE still trails (2.51 vs 1.59) — gap narrower, not closed. Full story: `data/evolution/19-respiratory-rate-ground-truth.md` Findings 7-8, clean summary in `data/RR_PAPER_NOTES.md`.
  - **A synthetic RR self-test now exists** in `scripts/validate_dataset.py` (runs by default; `--skip-rr` to skip). RR previously had NO automated regression test, which is how a filter passing 42-60 br/min survived the project's entire history, and it's what caught both bugs in the bullet above. It imposes all three RIVs including true phase-integrated RSA, so a single broken channel cannot pass unnoticed. **The display/aggregation suppression gate (`rr_conf < 30` in `web/routes.py` and `scripts/analyze_video.py`) must stay matched to `core/clinical.py`'s `RR_CONFIDENCE_LOW`** — it used to be a looser `< 10`, which let band-edge lock-on readings (the exact "bounces to 6 or 30" failure `_estimate_rr`'s docstring describes) display as solid-looking numbers the clinical engine had already privately flagged as unreliable. If you touch either threshold, touch both, or the display and the clinical reasoning will disagree about the same reading again. See `data/evolution/17-live-session-hardening.md`.
  - **First real live-webcam RR test (Finding 10) returned `final_rr=None` all session — root-caused, not just "webcam is noisier."** With RIFV dropped, the fusion has exactly 2 channels (RIAV, RIIV), and the agreement check is a hard binary: `spread <= 2.0 br/min` gets real confidence, `spread > 2.0` is capped at 25 (below the 30 gate) with **no reachable middle ground** — for 2 candidates the "tightest pair, reduced confidence" branch is mathematically dead code (its own comment says so). A live session's actual numbers: RIAV stayed rock-stable at ~12 br/min all session (plausibly the real rate); RIIV started near it, then drifted 10.6 -> 6.4 br/min, opening a gap the gate can't tolerate. Working hypothesis: RIIV is raw ROI pixel-brightness, which any consumer webcam's continuous auto-exposure/AGC will drift independent of true blood-volume change — a confound BIDMC/CapnoBase's contact-PPG-derived RIVs never had to survive, since there's no camera exposure loop in that signal path at all. **Not fixed** — no threshold/fusion change should ship without re-running `validate_rr_bidmc.py`/`validate_rr_capnobase.py` afterward, which has deliberately not been done. Full story and candidate directions (locking webcam exposure, weighting RIAV over RIIV on disagreement, deriving RIIV from a less exposure-dependent channel): `data/evolution/19-respiratory-rate-ground-truth.md` Finding 10.
- **RR search band is now HR-adaptive, plus a low-zone peak rescue (Finding 11; `_rr_band`, `_select_rr_peak`, `_RR_BAND_*`, `_RR_LOW_ZONE_*` in `core/rppg.py`).** Session MAE: BIDMC 1.61 -> 0.96, CapnoBase 2.45 -> 1.84, synthetic RR 7.2 -> 4.4, and on 40 VitalDB surgeries used ONLY as a held-out test, 1.21 -> 1.03. Band edges are 0.06x / 0.30x the window's own beat-derived HR (clipped to 0.10-0.25 / 0.50-0.80 Hz); the rescue looks for a peak at 1.6-2.8x a winning peak below 12 br/min instead of only the exact-2x bin. **Do not tune further on BIDMC/CapnoBase alone** — the optimum differs by population (BIDMC wants a higher floor, CapnoBase's children want a higher ceiling), and every extra knob tested after this one (lower ceiling floor, soft RR/HR prior, RIFV as tie-breaker, cross-channel verification, session spectrum averaging, tracker, top-K matching, fused spectrum) traded error between populations instead of reducing it. Known regressions of this fix: CapnoBase `0016`/`0029` (true ~10 br/min with a real 2x harmonic). Remaining worst: CapnoBase `0115` (26), `0370` (15), `0149` (11); BIDMC `bidmc_36`/`43`. SmartFusion still beats us on CapnoBase (1.59 vs 1.84) because it uses RIFV, which helps children and hurts adult ICU patients.
  - **A learned peak re-ranker (HistGradientBoosting over per-candidate physiological features) was built and NOT shipped.** Leave-one-population-out over 7 groups: mean session MAE 1.34 (shipped rule) -> 1.11 (learned), winning 5 of 7 — but all 5 wins are VitalDB age groups that share a hospital/sensor with the training data (20-50% lower); on the two independent sources it is WORSE (BIDMC 0.96 -> 1.62, CapnoBase 1.84 -> 1.92). It generalizes across ages within one data source, not across sources — and a webcam is a different source. Revisit only with webcam paced-breathing data as training/validation. Exporting such a model must be numpy-only (no joblib/pickle): the HR correction model has failed to load twice (sklearn 1.7.2 -> 1.9.0 `_loss`, then an Application Control policy blocking `_bitset`).
- **`core/clinical.py::assess()`'s entry gate is `if hr <= 0:` only — do not recombine it with `rr <= 0`.** It used to be `hr <= 0 or rr <= 0`, which discarded a perfectly good, confident HR reading entirely any time RR was zeroed (which happens routinely now that the RR gate above is stricter) — never reaching the isolated-tachycardia/bradycardia branches further down that already handle `rr == 0` correctly (shock is auto-disabled since it requires both vitals). Found live: a 107 BPM / 84% stability session triaged to "Insufficient signal for clinical assessment." Verified against all 8 scenarios in `scripts/evaluate_agent_reliability.py::SCENARIOS` (unchanged — none of them exercise "good HR, no RR") plus the regression case itself. Full story: `data/evolution/17-live-session-hardening.md`.
- Skin-tone stratified accuracy — still not computed. None of the three datasets currently in `test/` ship per-subject skin-tone metadata (rPPG-10 does have Fitzpatrick labels in its `Subject Data.xlsx`, but rPPG-10's videos can't run through the face-detection pipeline at all — see `scripts/validate_cropped_roi.py`'s docstring). The README's "Fitzpatrick Inclusivity" language is a design goal, not a validated result — keep it phrased that way.
- **Agent narration faithfulness (`scripts/evaluate_agent_reliability.py`) — the LLM layer restates `priority_score` correctly only 6.2% of the time** (16 real runs, `meta/llama-3.1-8b-instruct`), even when explicitly told to copy the given number verbatim. ESI level (81.2%) and shock flag (93.8%) fare much better. This is the empirical justification for the "one rule that matters most" at the top of this file — full numbers in README's Agent Narration Faithfulness section, full story in `data/EVOLUTION.md` Era 8.
- **`Camera.get_frame()` in dummy_mode never returns `frame_bytes=None`** (by design, for the live MJPEG stream — it should keep showing a placeholder rather than end). Any NEW code that loops on `frame_bytes is None` as its stop condition (like `analyze_video_complete()` used to) will hang forever if the source fails to open. This caused a real 2h20m infinite loop when a test script passed a bad path and the LLM called a tool with it despite being told not to. Fixed in `analyze_video_complete()` with an immediate `camera.dummy_mode` check plus a hard 100,000-frame cap — if you write another function that loops on `camera.get_frame()`, check `dummy_mode` first, don't rely on `None` alone.
- **The hybrid ML correction model is now wired into the live webcam path, not just offline batch validation/uploads.** It used to be true that "the live product app has no ML correction model loaded at runtime" — that changed: `web/__init__.py` loads `models/bpm_correction_gbr.joblib` once at startup, `web/routes.py::generate_frames()` runs every high-SQI live cycle through it (accumulating `session.corrected_bpm_history`), and `agents/tools.py::get_vitals_dict()`'s live branch uses the IQR-filtered median of that history as `bpm` once ≥3 corrected readings exist, falling back to the classical average otherwise. This reuses the exact model/feature schema validated offline at 6.48 BPM MAE (Era 12), but there is no separate live-webcam ground-truth dataset confirming that number holds identically for a live camera stream vs. the UBFC-rPPG/UBFC-Phys source video it was trained/validated on — treat it as the same proven model applied to a structurally similar but not identical input distribution, not a re-validated result. See `data/evolution/17-live-session-hardening.md`.
- Live camera is single-session by design (`web/__init__.py` holds one global `camera`/`rppg_engine`/`session`) — this matches "one workstation, one webcam," but means the "dynamic triage queue" is a sequential log of completed runs, not concurrent multi-patient live monitoring. Don't describe it as the latter.
- Batch validation over very long videos needs `process_stride` (see rPPG-10's `validate_cropped_roi.py`, stride=3) — running the full DSP pipeline (Welch FFT + cubic-spline HRV) every single frame turned a 10-minute video into 13+ minutes with zero results. But `process_stride` is NOT free to use anywhere — see the harmonic-lock-on writeup above for why `validate_dataset.py`'s manifest path deliberately stays at stride=1 (default): the BPM lock/subharmonic logic counts in cycles, not time, so striding changes tracking *behavior*. The live product path (`agents/tools.py` → `analyze_video_complete(video_path)`, no stride arg) is unaffected either way.

## Kiosk, waiting room, theme — what to know before touching them

Full build story, measurements and the NOT-verified list: `data/evolution/20-voice-and-kiosk-ideation.md`. Short version:

- **Patient kiosk** (`/kiosk`, rehearse with `?demo=1&skip=1`): voice-guided intake (name, age, sex, complaint) -> positioning guidance -> 90 s scan -> token + queue position, spoken in pre-rendered Sonia clips (`frontend/public/voice/`, re-render with `tools/tts_lab/render_prompts.py`). All logic is in `frontend/src/lib/kiosk/flow.ts`; `guidance.ts` is pure and unit-tested (`cd frontend && node --test src/lib/kiosk/guidance.test.ts`). Voice and touch always race — typing is the floor.
- **Tokens/queue**: `save_new_patient()` allocates the token and saves in ONE statement (`uq_token_per_day` unique index makes a lost race retry). `/api/triage_run` with `fast:true` returns in ~3 s and fills the AI narrative in later. `GET /api/waiting_room` is public and token-only; staff actions are `/api/queue/call_next`, `/api/queue/mark`, `/api/patients/<id>/status`.
- **Do not add per-query round trips to `web/neon_db.py`.** Neon costs ~0.9 s per query / ~1.8 s per new connection from here; the layer uses a connection pool + autocommit for exactly that reason. Never end a read with `conn.rollback()`.
- **LLM models are not hardcoded.** NVIDIA's per-key model access changed several times in one evening (410 retired, 404 not entitled, sudden timeouts). `agents/llm_pool.py` probes and ranks; add candidates there. If the whole pool is dead the deterministic triage still works and the narrative degrades to deterministic text.
- **Restart servers by killing the old process first** (look up `app.py` via `Get-CimInstance Win32_Process`) — stray duplicates on port 5002 caused inconsistent behaviour.
- **Theme**: ONE theme only, warm white + orange (user decision, no dark mode, no toggle). Colours live in the `:root` tokens in `globals.css`; each vital has a fixed signal colour (`--sig-hr` green, `--sig-rr` orange, `--sig-stress` pink, `--sig-sqi` blue). The dashboard's hard-coded Tailwind colours are remapped by the `.vital-app` layer there — to change the look, change tokens; don't re-add per-component colours or a second theme. The Vitals monitor is `components/BedsideMonitor.tsx` + `.bm-*` styles (alarm limits there mirror `core/clinical.py` — keep in sync). Don't put a `filter: blur()` on the animated full-screen background layer: it made every frame repaint and stalled rendering. `frontend/src/app/page.tsx` has **CRLF** line endings: normalise `\r\n` before multi-line scripted edits or they silently fail to match.
- **Pediatric thresholds (done 2026-10-30):** `core/clinical.py::assess(age_years=...)` picks HR/RR limits from `AGE_BANDS` (tachycardia/tachypnea = ESI v4 danger-zone vitals; bradycardia = PALS normal-awake lower bounds). `age_years=None` = adult limits, so the dashboard and offline scripts are unchanged — verified bit-identical over a 1,620-case adult grid. The kiosk passes its recorded age through `triage_run`. **Every patient under 18 gets `needs_manual_review=True`**: the camera has never been validated on children, and for infants the danger limits (HR >180, RR >50) are at or above what the DSP can report (`MEASURABLE_HR_MAX`/`MEASURABLE_RR_MAX`, from `_BP_HIGH_CEIL` and `_RR_BAND_HI_CAP_HZ`). If you widen those DSP ceilings, update the two constants too.

## HR research lab (Era 21) — read `data/evolution/21-hr-data-audit-and-plan.md` first

- **The face tracker in use is the Haar cascade, NOT MediaPipe** (found 2026-10-30). mediapipe 1.0.1 (installed
  2026-08-15) removed `mp.solutions`; `core/camera.py` detects that and falls back to Haar with only an INFO log.
  All 125 cached sessions — and, since the replay reproduces them exactly, the 71-session 9.43 / 6.48 results — were
  produced with Haar ROIs. Haar finds the face in only 6-54% of frames on several of the worst-error sessions
  (ph_s11_T2 5.9%, ph_s9_T3 33.5%, ph_s33_T3 36.2%, d2_subject15 53.9%). Do not describe the deployed ROI extraction as
  "MediaPipe face mesh". `scripts/tasks_face_mesh.py` adapts the new MediaPipe Tasks FaceLandmarker to the old
  interface so the camera's ORIGINAL landmark ROI code runs unchanged; it needs `dataset/models/face_landmarker.task`.
  `dataset/cache/run_mp.sh` re-tracks all sessions with it and writes `HR_RESULTS_MP.md` + `TRACKER_COMPARISON.md`.

- **Ground truth for UBFC-rPPG was partly corrupted**: the oximeter HR column has dropouts (0 / 7 BPM readings) and
  the old session truth was its MEAN. `hr_data.reference_info()` uses the median of valid (40-180) readings and flags
  sessions with >10% impossible readings. The rule uses the reference device only, never our estimates. Always report
  original AND cleaned labels.
- **Cache first, then replay.** Face tracking is ~all the cost (5 min per 3-min UBFC-Phys clip); `hr_replay.py` reproduces
  the old classical results exactly from the cache. New ideas are tested by replay in minutes, never by re-tracking.
- **Peak selector (`hr_peaks.py`)**: chooses among real spectral peaks of CHROM and POS (lock-independent spectra via
  `AdvancedRPPG.capture_spectra`, off by default) instead of regressing a value, so it cannot shrink toward the mean.
  Evaluated out-of-fold by subject. As of Era 22 it IS wired into the app, as half of the `core/hr_ensemble.py` selector+tracker mean (numpy-only models in `models/hr_*.npz`; `VITAL_HR_ENSEMBLE=0` disables; ~3.8-3.9 BPM out-of-fold on video, pair picked post hoc, NOT live-webcam validated — read `data/evolution/22-hr-ensemble-integration.md` before quoting a number). Do not claim it generalises until the cross-dataset rows
  in `HR_RESULTS.md` pass (the RR learned re-ranker passed within-source CV and failed across sources).
- `AdvancedRPPG.capture_spectra` and `Camera.record_roi_parts` are research hooks, default off; verified the synthetic
  check is unchanged (HR 0.29/0.53, RR 4.44) and BIDMC RR unchanged (0.96 / 0.39).

## Live webcam (Era 23) — read `data/evolution/23-live-webcam-fps-and-rr.md`

- **The DSP assumes one fixed fps and ignores timestamps.** A webcam's driver-reported fps is nominal (here -1 -> 30) and the real loop rate
  was 9.6-11.5 fps, which scaled every frequency by 3x and starved RR. Live frames now go through `core/live_resampler.UniformResampler`
  (`web/routes.py::_run_dsp`) onto a uniform 30 Hz grid; files are unchanged. Verified offline at 6-120 fps (`scripts/test_live_resampler.py`),
  NOT yet on a long live run. Do not feed live frames straight into `AdvancedRPPG`, and don't let several browser tabs pull `/video_feed`
  while testing — they share one `Camera` and corrupt each other.
- **Live RR is still wrong (counted ~22, app showed 7 at 1% confidence).** RIIV locks on exposure drift near the band floor and early
  coincident readings stay in `rr_history` forever. Unfixed on purpose (one counted session cannot validate a tuning). Claim respiration
  on recorded data only (BIDMC / CapnoBase / VitalDB), never on a live webcam.
- `core/hr_ensemble.py` (Era 22) is wired into the app; `VITAL_HR_ENSEMBLE=0` disables it. `scripts/test_hr_ensemble.py` checks parity.

## A note on trusting changes in this repo

Mid-session, the BPM lock/candidate hysteresis fix above was implemented, and its *first* version silently regressed two previously-correct synthetic cases (introduced a same-value streak-counter design that was too fragile against ordinary FFT-bin jitter). It was caught immediately by re-running `scripts/validate_dataset.py` after the change, not by inspection. **The lesson: re-run the validation harness after any change to `core/rppg.py` or `core/clinical.py`, every time, before considering a change safe.** A change being reviewed and appearing reasonable is not the same as it being verified.

```bash
python scripts/validate_dataset.py                                          # synthetic self-test, HR **and** RR — run this after ANY core/rppg.py change
python scripts/validate_dataset.py --manifest test/manifest.csv --skip-synthetic  # real 56-session set, if test/ dataset is present locally
python scripts/validate_cropped_roi.py test/rPPG-10                        # DSP-only, separate — see README for why it's not comparable to the above
python scripts/validate_rr_bidmc.py --baseline --stride 3.0                 # real RR ground truth (53 recordings) — run after ANY change to the RR path
```

Expected current values, so a regression is obvious: synthetic HR **0.29 BPM
MAE / 0.53 RMSE**; BIDMC RR **session MAE 0.96 / median 0.39**; CapnoBase RR
**session MAE 1.84 / median 0.06** (`scripts/validate_rr_capnobase.py`); synthetic RR
**~4.4 br/min MAE** (still worse than real — an open item, see Era 19); VitalDB RR
(40 held-out surgeries, never tuned on) **session MAE 1.03 / median 0.24**. These are
after Finding 11 (HR-adaptive RR search band + low-zone peak rescue); before it they were
1.61 / 2.45 / 6.9-7.2 / 1.21. **The datasets moved to `dataset/rr/` and `dataset/hr/` —
both RR validation scripts still default to the old `dataset/` path, so pass `--root`.**

**Landmine to know about before touching filters:** `_safe_butter_sos()`
applies *heart-rate* band guards by default (`_BP_LOW_FLOOR = 0.70` Hz). Any
call for a band outside the pulse range must pass
`clamp_to_pulse_band=False`, or the requested band is silently rewritten —
the respiration request for 0.10-0.50 Hz became a **0.70-1.00 Hz (42-60
breaths/min)** filter centred on the heart rate, which is what made the old
RR estimator measure nothing at all for the project's entire history.

## Style/process notes specific to this repo

- The user has been building this iteratively with AI assistance and values direct, unhedged honesty over reassurance — when something doesn't work, say so plainly with the evidence, don't soften it.
- Prefer running the real datasets in `test/` (56 real sessions across UBFC-rPPG + UBFC-Phys, plus 26 more via the separate rPPG-10 DSP-only path, all built via `scripts/build_manifest.py`) over synthetic-only claims whenever making an accuracy statement — synthetic validation only proves the DSP math, not real-world camera+face-detection accuracy.
- When running multiple batch validation jobs, run them **sequentially, not concurrently** — two MediaPipe/OpenCV processes fighting for CPU at once was directly observed to make both crawl to a near-halt (a video that normally processes in ~1-2 minutes took 45+ minutes with zero results when two jobs ran in parallel).
- The project's own `venv/` already has the heavy deps (`opencv-python`, `mediapipe`, etc.) installed and working — use `./venv/Scripts/python.exe` (Windows) rather than trying to reinstall a fresh environment.
- Windows console encoding: avoid non-cp1252 characters (emoji, `✓`, box-drawing beyond em-dash) in anything passed to `print()` in scripts meant to run in a plain Windows terminal — this caused a real crash in `scripts/analyze_video.py` mid-project. Em-dashes (`—`) are fine; checkmarks/emoji are not.
