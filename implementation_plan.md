# VITAL: Restructuring to a Next.js & Python SaaS Architecture

This updated plan details the integration of a **Next.js frontend** (in a `/frontend` subdirectory) with our **Flask Python backend** (running on the root) to create a premium SaaS application. 

To satisfy the academic requirement of **novelty**, our agents will directly address key limitations identified in the 30 IEEE research papers in your `research/` directory.

## 🛠️ The Novelty Strategy (Solving Paper Limitations)

Our product will target and resolve three specific limitations from the IEEE literature reviews:

1. **Tabular Note Sparsity / Incomplete Data** (*Arnaud et al. 2020; Fakhfakh-Maala et al. 2022*):
   * *Our Solution (now actually implemented, `core/clinical.py`)*: a deterministic multiplicative interaction term `tachy_hr(HR) × tachy_rr(RR)` — a real polynomial cross-correlation, computed in code, not generated by an LLM. Missing-narrative inference is handled by `core/guidelines.py`'s local term-frequency retrieval over the research corpus, not the FAISS/OpenAIEmbeddings-style RAG originally implied here — see that module's docstring for the honest scope of what "RAG" means in this codebase.
2. **Clinical Alert Fatigue & Lack of Explainability** (*Liu & Tsai 2024; Jonatha & Lubis 2025*):
   * *Our Solution*: The **Diagnostic Agent** narrates the deterministic assessment's reasoning trace, grounded in retrieved ESI/WHO guideline snippets — it does not compute the ESI level itself (see Post-Audit Corrections below for why that distinction matters).
3. **Ineffective Static Queuing (FIFO)** (*Esan & Elegbeleye 2024; Sandal et al. 2025*):
   * *Our Solution*: The **Coordinator Agent** restates a priority score computed deterministically from ESI band + continuous shock-risk score, so patients within the same ESI band still order by severity rather than a flat 5-bucket sort. Note: this reorders a *sequential log* of completed triage runs, not concurrent multi-patient live monitoring — see Post-Audit Corrections.

## 🩺 Post-Audit Corrections (retroactive — read before citing this plan)

An honest review after the initial build found several claims in this document didn't match the shipped code. Fixes, in the same files this plan describes:

* **ESI/shock classification was LLM-guessed, not computed.** The Coordinator Agent emitted free-text JSON, regex-parsed, silently falling back to `esi_level=3` on any parse failure — the most safety-critical number in the system was non-deterministic. Fixed: `core/clinical.py` now computes it in plain Python; the LLM only narrates.
* **RAG was never built.** Fixed with an honestly-scoped alternative: `core/guidelines.py`, local TF-cosine retrieval, not vector embeddings.
* **File-based triage runs never captured RR/HRV/stress_index** (`scripts/analyze_video.py` only tracked bpm/confidence per frame) — meaning Compensated Shock detection was structurally impossible for any uploaded video, only for live sessions. Fixed alongside the above.
* **The shared `triage_crew` Crew object was not safe for concurrent Flask requests** (CrewAI `Task` objects store output on `self`). Fixed via `agents/crew.py::build_triage_crew()` — a fresh Agent/Task/Crew set per call.
* **POS mode has a real, now-measured accuracy problem** (harmonic lock-on under sensor noise at HR ≲ 90 bpm) and was already unreachable from the API/UI despite being described as a feature. See README's Validation section for the actual MAE/RMSE numbers.
* **No dataset-level MAE ever existed** — `scripts/validate_dataset.py` defaulted unlabeled videos to `gt_bpm=0` and printed the resulting distance as if it were an accuracy metric. Replaced with a synthetic known-BPM self-test (real numbers, see README) plus a `--manifest` mode for real datasets once obtained.
* **CORS was `origins: "*"` and the whole-database `DELETE` endpoint was unauthenticated.** Fixed with a configurable origin allowlist and an opt-in `API_KEY` gate.

## 🚀 Step-by-Step Implementation Roadmap

### Phase 1: Clean Up & Python Restructuring
1. Relocate `camera.py` and `rppg.py` under `core/`.
2. Create `agents/` directory containing `crew.py`, `tools.py`, and YAML configs.
3. Move utilities `analyze_video.py`, `validate_dataset.py`, and `open.py` to `scripts/`.
4. Update `app.py` to serve purely as an API server (disabling HTML templates).

### Phase 2: Complete the Multi-Agent Crew Configurations
1. **`agents/config/agents.yaml`** and **`agents/config/tasks.yaml`**: Define YAML attributes for Perception Agent, Diagnostic Agent, and Coordinator Agent.
2. **`agents/crew.py`**: Create the updated Crew class that dynamically loads agents/tasks from YAML config.

### Phase 3: Next.js Frontend Initialization
1. In accordance with guidelines, first query `npx create-next-app --help` to examine setup flags.
2. Create the frontend folder: `npx create-next-app@latest frontend --typescript --eslint --tailwind --src-dir --app --import-alias "@/*"` (using non-interactive flags).

### Phase 4: Build the Next.js SaaS Interface
1. **Biometric Dashboard**: Build a gorgeous interface with CSS transitions, real-time vital gauges, and an interactive canvas for the rPPG signal plot.
2. **Dynamic Triage Queue**: Create a live queue component that polls `/status` and `/session_summary` from the Flask API, sorting patients by ESI acuity.
3. **OptiBot AI Assistant**: Integrate voice recording (Web Audio API) and text chat connected to `/api/chat` with Gemini.
4. **Multimodal OCR & Document Analysis**: Add a file attachment UI in Next.js `page.tsx` and image parsing logic in Flask `routes.py`. The backend will parse the image and perform native OCR/reasoning through Gemini's vision capability.
